Sello design system

The design system, as built

What Sello looks like today, read from the code and its committed screenshots: tokens, shared components, and every feature's screens and states.

What this is

This is a description of the built app. The source for every statement is the Kotlin code in :design-system and :app, and every picture is a screenshot baseline the tests draw and CI compares. When a page and the code disagree, the code is right and the page is out of date.

Prose is in English. Interface text is quoted in Spanish exactly as it is in the strings.xml files.

Screenshots are linked from where the tests write them, never copied: app/src/test/screenshots/ and design-system/src/test/screenshots/. Re-recording a baseline updates these pages. A link to an image that does not exist shows a red missing screenshot box, so a renamed or deleted baseline is easy to spot.

How to open it

Serve the repository root and open this page; no internet connection is needed (the fonts are the ones bundled in design-system/src/main/res/font/).

python3 -m http.server 8765 --bind 127.0.0.1
# then open http://127.0.0.1:8765/docs/design/system/index.html

Opening the files straight from disk does not work: the icons on Foundations are read from the drawable XML files, which a browser only allows over HTTP.

How the pages are organised

  • Foundations: the colours of both inks (Cobalto, Violeta) in light and dark, the type scale, shapes, spacing, motion and icons, from design-system/…/theme and design-system/src/main/res.
  • Components: every public @Composable in :design-system, with its source line, purpose, parameters, the features that use it and its screenshot (or a gap where none exists). Each has an anchor components.html#c-Name.
  • Findings: where a component is used against its meaning, where a shared component is copied by hand, and where a value is hard-coded instead of a token.
  • One page per feature under features/ (the nav lists them all): purpose, entry points, each screen with every state the code has, the components it uses and why, and its gaps.

How the screenshots are produced

The JVM screenshot tests (Robolectric, drawn at one pixel per dp) write the baselines; CI's host gate compares every capture with its committed image (see quality gates). To record them again, on Linux as CI does:

./gradlew :app:recordRoborazziDebug --no-build-cache --rerun-tasks
./gradlew :design-system:recordRoborazziDebug --no-build-cache --rerun-tasks
